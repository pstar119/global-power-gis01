## 4. 下一步工作（按顺序）

### 第 1 步（✅ 已完成 2026-09-24）：`osm_ids` 上限 20 → 5，并重测体积

**改动**：`scripts/lib/merge-lines.mjs` —— `mergeLines(features, { maxOsmIds })` 默认 **5**，
并把它**真正传进** `decorate()`（原先 `decorate` 里写死 `slice(0, 20)`，参数形同虚设、改了没效果）。
单测补 2 条（默认截断 + 参数真的生效），13/13 通过。

**实测结果 —— 与本文档原先的预期不符，务必按实测记：**

| 归档 | 改前（cap 20） | 改后（cap 5） | Δ |
|---|---|---|---|
| 华东 huadong | 26.65 MB | 26.61 MB | −0.04 |
| 华中 huazhong | 17.83 MB | 17.77 MB | −0.06 |
| 华南 huanan | 12.95 MB | 12.89 MB | −0.06 |
| 华北 huabei | 18.96 MB | 18.94 MB | −0.02 |
| 东北 dongbei | 12.74 MB | 12.72 MB | −0.02 |
| 西南 xinan | 32.48 MB | 32.29 MB | −0.19 |
| 西北 xibei | 30.47 MB | 30.39 MB | −0.08 |
| **7 包合计** | **152.08 MB** | **151.61 MB**（158,978,656 B） | **−0.47 MB（−0.31%）** |
| 核心区 osm_grid | 7.020 MB | 7.015 MB（7,355,653 B） | −0.005 |

⇒ **"上限 20→5 能让体积明显回落"这个预期是错的**（本文档原话已按实测修正）。

**为什么错（华东实测分解，同一份合并后 GeoJSON 只改 `--keep-props` 重切）：**

| 保留的属性集 | 体积 |
|---|---|
| 基础属性（无合并三字段） | 21.09 MB |
| + `merged_count` | 21.63 MB（+0.54） |
| + `osm_ids` | 23.07 MB（+1.98） |
| + `length_km`（含 merged_count） | 24.82 MB（`length_km` 单独 +2.65） |
| 三者全带（= 现状） | 26.61 MB |

- 真正的大头是 **`length_km`（非整数 ⇒ MVT 存 double，8 字节/要素）** 与 **`osm_ids`（每要素唯一 ⇒
  字符串表无法去重）**，`merged_count` 最小。
- `osm_ids` 上限 20→5 之所以几乎没效果：合并率只有 12~17%（华东 74,994 → 63,994），
  **绝大多数要素 `merged_count=1`**，逗号串本来就只有 1 个 id —— 上限截断只影响极少数长链。
- 顺带证实：**几何合并本身是减体积的**（华东 21.09 vs A1 未合并的 21.71 MB，−0.6 MB），
  +4.9 MB 全部来自那三个新字段。
- ⇒ 真要压体积，得动 `length_km` 的**表示**（如整数米）或不再落 `osm_ids`；两者都改设计契约（§4.1/§5.2），
  **未获授权不做**。当前取舍：接受 151.61 MB。

**门禁（本次全部重跑，逐个归档）**：7 包 + 核心区各跑
`verify_power_only.mjs`（geojson 与 pmtiles 两次）+ `verify_pack.mjs` ⇒ **24 项断言全绿、零失败**
（最大单瓦片 250~397 KB < 500 KB；z≥8 专属属性与扩容属性命中；无空属性值；解码 0 失败）。

## 5. 硬约束与踩过的坑（**别重新踩**）

| 约束 | 说明 |
|---|---|
| **切片参数** | 区域包必须显式带 `--max-features-per-tile 20000 --cap-below-zoom 8`；**缺了会产出未封顶包**（实测 z4 单瓦片 922.9 KB），被 `verify_pack.mjs` 判失败 |
| **核心区归档** | `--name core --out src-tauri/resources/maps/osm_grid.pmtiles`，**反过来必须不带封顶**（按设计不封顶） |
| **`--out` 必须显式** | `build_pmtiles.mjs` 默认输出写死为 `osm_grid.pmtiles`，不给 `--out` 会**静默覆盖核心区归档** |
| **两道属性白名单** | `prepare_osm_geojson.mjs` 的 `KEEP_PROPS` 与 `build_pmtiles.mjs` 的 `keepProps` **必须同步**（阶段42 与本次都因只改一处而静默丢字段） |
| **MVT 不支持数组属性** | 所以 `osm_ids` 存成逗号串；`undefined` 属性会让 MapLibre **整张瓦片放弃解析** |
| **不重抓就能改数据** | 铁路/管道、属性扩容、几何合并都**不需要重抓**（中间产物在 `data/osm/`） |
| **验证脚本是门禁** | `verify_power_only.mjs`（GeoJSON 权威内容 + 归档结构）、`verify_pack.mjs`（体积/不丢数据/属性存在性）、`verify_fetch_categories.py`（无死代码）；每次重建后对 **7 包 + 核心区逐个跑** |

### 两个"渲染上看不出来"的缺陷（务必记住教训）

1. **性能**：邻接表建在分组循环内 ⇒ O(组数×端点数)，华东 75k 线**跑满 600 秒超时**；移到循环外后 2 秒。
2. **正确性**：几何合并的方向对齐对"同点起始的 V 形拐点"静默退化，**丢 9.5% 总长**（验收口径 0.1%）。
   两者在渲染上都完全正常 —— **只有数值断言（长度守恒）与计时能抓到**。
