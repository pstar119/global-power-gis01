## 1. 背景与目标

### 1.1 起因

对照 OpenGridWorks（[opengridworks.com](https://opengridworks.com/)）的显示程度后得出的结论是：
**渲染与交互层本项目已基本具备**（燃料配色、容量分档气泡、电压分档线路、弹窗、视野统计、图例与图层控制），
真正的差距在**数据面的覆盖范围**。

全球复刻的成本主要花在两类本项目根本用不到的抓取上：美国专属源（EIA / HIFLD）与大量 OSM 稀疏区。
⇒ 改为先做**中国 + 相邻带邻国**，把力气花在能用相邻带数据说话的地方。

### 1.2 目标（本设计要交付的）

1. **5 个邻国电网数据包**，与国内 7 个区域包**完全同构**（同管线、同切片参数、同分发机制、同运行时装载方式）。
2. **5 个同 bbox 的邻国底图包**，作为**第三类数据包**（`kind: "basemap"`）按需下载。
3. **多文种离线字形**：在中文字形之外补齐韩 / 日 / 泰（西里尔实测后决定），使邻国地名不再出现方块。
4. **运行时装载规则放宽**：区域包同时装载上限 2 → 3，避免边境带"一侧有网、一侧空白"。
5. **中国侧零回归**：核心区优先、区域选举、图层面板行为与阶段 54 一致。

### 1.3 非目标（明确不做，避免范围漂移）

| 不做的事 | 理由 |
|---|---|
| 全俄（`19.6,41.2,180,81.9`） | 单独 2,835 块 / ≈39.6 小时，是全部邻国成本的 2.5 倍；本轮只做与中国相邻的纬度带 |
| 南亚（印/巴/尼/不/孟/斯）、阿富汗 | 用户选定范围为"相邻带最小集"，南亚不在内 |
| 海上邻国（日/菲/马/印尼） | 同上；`jp` 批次已在估算表里，后续可独立加 |
| 美国 / 全球铺开 | 需要 EIA/HIFLD 等美国专属源，是另一条数据路线 |
| 把底图与电网**合成同一个 PMTiles** | 需要 MVT 逐瓦片合并，属对 `build_pmtiles.mjs` 的实质改造，本轮不做 |
| 新增任何 npm / cargo 依赖 | 项目红线；本设计全部复用既有工具（字体走 fontsource CDN 下载到本地、底图走已在用的 Protomaps 源） |
| 修改 Rust 侧 | 已确认不需要（见 §5.4） |

## 3. 数据面设计（§1 已与用户确认）

### 3.1 批次定义

在 `scripts/pipeline_regions.mjs` 的 `REGIONS` 追加 5 条（bbox 格式与现有一致：西,南,东,北）：

| key | label | bbox | 网格 | 块数 | 预估抓取 |
|---|---|---|---|---|---|
| `kp-kr` | 朝鲜半岛 | `124.3,33.1,131.0,43.1` | 6×5 | 30 | 0.4 h |
| `mn` | 蒙古 | `87.7,41.5,119.9,52.2` | 27×6 | 162 | 2.3 h |
| `sea-mainland` | 中南半岛 | `92.2,5.6,109.6,28.6` | 15×12 | 180 | 2.5 h |
| `ca` | 中亚五国 | `46.5,35.1,87.4,55.5` | 34×11 | 374 | 5.2 h |
| `ru-far` | 俄相邻带 | `80.0,49.0,145.0,62.0` | 55×7 | 385 | 5.4 h |

合计 **1,131 块 / ≈15.8 小时**（按项目实测 `50.3 秒/块` 外推；单块耗时由服务端负载主导，与要素数几乎无关）。

> ⚠️ 工期是**外推不是承诺**：设计期间实测过一次 Overpass `504`（服务器繁忙）。
> 缓解见 §7 风险表第 1 条 —— 按批次交付、断点续跑。

### 3.2 bbox 与国界的已知偏差（必须写进文档，别让后人当成 bug）

现有管线**只支持 bbox**，不支持按国界裁剪。因此：

- `ca`（`46.5,35.1,87.4,55.5`）除中亚五国本身外，会**夹带**伊朗东北部、阿富汗北部、巴基斯坦北部、蒙古西南角与中国新疆西部；
- `sea-mainland`（`92.2,5.6,109.6,28.6`）覆盖缅/老/越/泰/柬（属"中南半岛"口径内的预期），并夹带中国云南与广西部分 —— 这部分与国内 `xinan`/`huanan` 包重叠，由区域选举与"最多 3 个包"承载；
- `ru-far` 的南界 49°N 会让**贝加尔湖以西的俄罗斯缺失**，这是既定取舍。

⇒ 这些是**设计内的偏差**，在 README 与向导文案里如实标注"覆盖范围按矩形，非国界"。

### 3.3 抓取与切片

- 抓取：`node scripts/run_pipeline.mjs --regions <key>`（既有脚本，支持 `--stage fetch,prepare,build` 与断点续跑）。
- 切片参数：**沿用国内区域包**（`maxzoom 12`、低级别单瓦片封顶 20000、`cap-below-zoom 8`），保证跨境可比。
- 清单：`scripts/gen_packs_manifest.mjs` 读 `REGIONS` 自动纳入，**不手改 `public/packs_manifest.json`**。

## 4. 底图包设计

### 4.1 生成

对 5 个批次各跑一次：

```text
node scripts/fetch_basemap.mjs --bbox <region.bbox> \
  --global-maxzoom 4 --region-minzoom 5 --region-maxzoom 8 \
  --out data/packs/basemap-<key>.pmtiles
```

- **源归档固定为 `https://build.protomaps.com/20260912.pmtiles`**（与现有底图同源 ⇒ 风格一致）；
  若该 build 下线，需换源并重跑，这一点写进 README。
- 每份底图包的**体积必须先实测再写进文档**（设计期只给出 10–40 MB 的区间，不当作事实）。

### 4.2 清单里的形状（运行时靠它找到"某区域的底图包"）

底图包在 `public/packs_manifest.json` 里新增一个字段 `forRegion`，**不做字符串前缀解析**
（靠 `key` 去猜归属会在改名时静默失效）：

```json
{
  "key": "basemap-kp-kr",
  "kind": "basemap",
  "forRegion": "kp-kr",
  "label": "朝鲜半岛 · 底图",
  "file": "packs/basemap-kp-kr.pmtiles",
  "bbox": [124.3, 33.1, 131.0, 43.1],
  "bytes": null, "sha256": null, "sizeMb": null, "features": null
}
```

- `bbox` 与同区域的电网包**完全一致**（运行时的叠加 source 直接复用它，不再算一次）。
- `features` 恒为 `null`：底图不是要素数据，不要造假数字。
- **`scripts/gen_packs_manifest.mjs` 需要新增一段**：扫 `data/packs/basemap-<regionKey>.pmtiles`
  产出上述条目（当前脚本只从 `REGIONS` 生成区域包 + 从 `data/packs/gem-plants.pmtiles` 生成 GEM 包）。
  与区域包同样遵守"本地文件缺失时沿用旧清单里的指纹并大声告警"的既有约定。

### 4.3 为什么不随安装包

现有底图仅覆盖 `[98,18,128,46]`。扩到相邻带后面积约 ×5.5，z5–8 体积从 26 MB 涨到约 140 MB
⇒ **会破 50 MB 安装包红线**，且国内用户被迫为邻国底图买单。
⇒ 底图包走与电网包同一套按需下载通道。

### 4.4 运行时装载（4a：独立叠加 source）

新增一个"底图包生命周期"，与 GEM 的独立生命周期同构：

- 当选中的区域包 `key` 存在 `forRegion === 该 key` 的底图包**且已安装**时，把它作为一个**独立 source** 叠加到地图上（判定用 `forRegion` 字段，不做 key 前缀解析）；
- 该 source 只挂 **earth / water / boundaries / places / roads** 若干图层，**压在中国底图图层之上、电网图层之下**；
- 现有 `BASEMAP_SOURCE`（`"basemap"`）的 URL、图层、样式**一行都不动**。

代价（已知并接受）：叠加层与现有底图的色调可能有细微差异；好处是**可随时回退**、回归面小。

## 5. 运行时的三处必改与两处取舍

### 5.1 必改一：`src/lib/packs.ts` —— 品类判定语义化

- `PackKind` 增加第三态 `"basemap"`。
- 现有注释规则是"运行时一律用 `=== "gem"` 判定，缺失自然落到 region 分支"。**这条规则在有第三类之后不再安全**（缺省仍是 region，但 basemap 不能再靠"非 gem"来排除）。
- 改为导出显式判定函数：`isRegionPack(p)`（`kind === "region" || kind === undefined`）与 `isBasemapPack(p)`，`isThematicOverlay(p)` 语义收窄为"gem"。

### 5.2 必改二：`src/components/WelcomeWizard.tsx:86`

```ts
const regionPacks = useMemo(() => packs.filter((p) => p.kind !== "gem"), [packs]);
```

这是 `packs.ts` 注释里**明确警告过的反模式**。加了第三类之后，**底图包会被当成区域包**列进向导。
⇒ 改成 `packs.filter(isRegionPack)`，并新增底图包的分组展示（与同 bbox 的电网包成组，标注两份体积）。

### 5.3 必改三：`src/pages/MapPage.tsx` 的区域选举（约 4360–4372 行）

选举过滤当前是 `.filter((p) => !isThematicOverlay(p))`。底图包既不是 gem 也不是区域包，
**会被选进 `activePacks`、占掉名额、并被当作 MVT 图层名 `grid` 挂载**（静默错渲染）。
⇒ 改成 `.filter(isRegionPack)`。

同时把 `PACK_MAX_ACTIVE` 从 `2` 改为 `3`（决策 6）。`PACK_MIN_ZOOM` **保持 6 不变**
（z < 6 的宏观视野仍由全球 z0–4 底图 + 电厂点承担；降低它会带来"只挂 3 个包、其余空白"的观感问题）。

### 5.4 不需要改的（已核实）

| 项 | 结论 | 依据 |
|---|---|---|
| Rust 侧 | 无需改动 | `safe_file_name()` 只放行 `.pmtiles`，底图包也是 `.pmtiles` |
| asset 协议白名单 | 已覆盖 | `tauri.conf.json` 的 `$APPDATA/packs/**` |
| 下载/校验/续传 | 完全复用 | `packs.rs` 与 `usePackDownloads.ts` 与品类无关 |
| 安装包体积 | 不受底图影响 | 底图包不进 `bundle.resources` |

## 6. 字形设计（多文种族）

### 6.1 现状

`scripts/fetch_glyphs.mjs` 只处理一族（`@fontsource/noto-sans-sc`），且**按当前底图**的 `places` 码位裁剪
（命中 86/101 个子集，2.1 MB）。README 已记录「1766 个码位里 23 个无字形：缅甸文、泰文、一个 CJK 扩展 B」。

### 6.2 改法

1. 把"字体族"从单一常量改为**配置数组**（每族：`family` 名 / fontsource CSS 地址 / CDN 基址 / 输出目录）。
2. 先加 **KR（noto-sans-kr）、JP（noto-sans-jp）、Thai（noto-sans-thai）** 三族。
3. **重扫 5 份新底图归档的 `places` 码位**，只下载命中子集（懒加载与体积控制方式不变）。
4. **西里尔单独立项核实**：先扫码位判断 `Noto Sans SC` 是否已覆盖；缺则加一族 `Noto Sans`。
   （不在设计里预设结论，以扫描结果为准。）
5. 样式侧：`text-font` 从单族改为**多族 fontstack**（`[SC, KR, JP, Thai]`）。MapLibre 会把 fontstack 拼成 CSS 字体族列表，
   由浏览器按字符回退 —— 因此**不需要 glyphs 服务器**，与现有实现路径一致。

### 6.3 体积与归属

- 预估 **+2–6 MB**（韩/日子集较大）；字体属前端资源，**随安装包**（"装完即用"不受影响）。
- 安装包 LZMA 后增幅预计 +1–2 MB，**仍在 50 MB 红线内**；实测后再写进文档。
